# Исследование API Cheburcheck

Основа документа: реальные ответы сервиса, снятые `tools/research-capture.sh` 2026-11-02 (хост cheburcheck.ru, nginx 1.27.5, HTTP/2),
плюс исходный код фронтенда сервиса (`frontend/src/lib/api/probe.ts`) и документация kb/probing.

Метки: **[LIVE]** подтверждено живым запросом, **[SRC]** исходник фронтенда, **[DOC]** документация сервиса,
**[2ND]** со слов сторонних клиентов (не проверено), **[ВЫВОД]** мой вывод из наблюдений.
Реальные образцы лежат в `app/src/test/resources/` (id в check-ответах заменены на `test-id-*`).

## 1. Эндпоинты

| Запрос | Ответ | Статус |
|---|---|---|
| `GET /api/v1/status` | 200 `application/json` | [LIVE] |
| `GET /api/v1/healthcheck` | 200 `text/plain`, тело `OK` | [LIVE] |
| `GET /api/v1/check?target=<IP, домен или CIDR>` | 200 `application/json`, статика + `id` | [LIVE для IP/CIDR; домен подтверждён предоставленным образцом] |
| `GET /api/v1/probe/{id}` | 200 `text/event-stream` (SSE), динамика | [LIVE] |
| `GET /api/v1/check?target=999.1.1.1` | **404** `{"code":404,"info":"Not Found"}` | [LIVE] |

Дополнительно у сервиса есть эндпоинты приёма отчётов Reporter и белых списков под API-ключом [DOC]; приложению они не нужны и не используются.
Лимитных заголовков (`Retry-After`, `X-RateLimit-*`) в успешных ответах не замечено [LIVE]. Заголовки ответов: `alt-svc: h3`, `x-frame-options`, `x-content-type-options`.

## 2. /status [LIVE]

```json
{"domain_count":1775999,"v4_count":178932936,"last_update":"2026-11-02T14:48:34.469211492Z","version":"1.5.5"}
```
`last_update` — время обновления баз (RFC 3339, наносекунды, UTC). `version` — версия API. Приложение показывает их на главной и в настройках.

## 3. /check — статическая проверка [LIVE]

Пример для `1.1.1.1` (id сокращён):

```json
{"id":"<JWT>","target":"1.1.1.1","target_type":"IPv4-адрес","blocked":true,"ips":["1.1.1.1"],
 "blocked_subnets":[],
 "cdn_providers":{"cloudflare":[{"provider":"cloudflare","cidr":"1.1.1.0/24","region":null}]},
 "geo":{"asn":"AS13335","country_code":null,"organisation":"Cloudflare, Inc.","city_geo_name_id":null,"location":"-"},
 "reverse_lookup":["one.one.one.one"],
 "complaints":[{"date":"2026-10-20","count":0}, ... 14 дней ...]}
```

| Поле | Смысл |
|---|---|
| `id` | JWT (HS256). Claims: `query_id`, `target`, `ip`, `aud:"check-context"`, `iat`, `exp` (**срок жизни 24 ч**). `query_id` совпадает с `id` в событии `started` и с `job_id` в результатах сканеров. Для приложения id непрозрачен: оно его не разбирает, не логирует и передаёт только в `/probe/{id}` |
| `target`, `target_type` | Что распознал сервис: `IPv4-адрес`, `IPv4-подсеть`, `Домен` |
| `blocked` | **Только членство в списках.** Для 1.1.1.1 это `true` из-за списка CDN, а сканеры при этом показывают «доступен» у большинства. Поэтому приложение не трактует поле как итог |
| `ips` | Адреса цели. Для домена это выданные сервисом A/AAAA адреса; для подсети сервис перечисляет хосты. ASN и организация домена в `geo` относятся к первому IP |
| `blocked_subnets` | Заблокированные подсети, в которые попал адрес (в образцах пусто, тип элементов не наблюдался; приложение показывает их как текст) |
| `cdn_providers` | Объект «имя CDN → список {provider, cidr, region}» |
| `geo` | `asn`, `organisation`, `country_code`, `city_geo_name_id`, `location` (`"-"` = нет данных). Поля часто `null` |
| `reverse_lookup` | PTR-записи |
| `complaints` | Жалобы пользователей за 14 дней: `{date, count}` |
| `subnet_size` | Только для подсети, **строкой** (`"256"`) |

Не встречались в образцах, но документированы сторонними клиентами и поддерживаются парсером: `rkn_domain`, `whitelist` [2ND].
Парсер читает JSON деревом: отсутствующие поля и поля неожиданного типа дают `null`, неизвестные ключи запоминаются (`unknownKeys`), исходный JSON хранится целиком.

Наблюдения [LIVE]:
- каждый вызов `/check` выдаёт **новый** `id`, даже для того же адреса;
- частный адрес `192.168.1.1` принимается: 200, `blocked:false`, пустой `geo`, пустой `cdn_providers`;
- для подсети JWT содержит `ip` первого хоста (`1.1.1.1`);
- некорректный адрес (`999.1.1.1`) даёт 404.

## 4. /probe/{id} — динамическая проверка (SSE) [LIVE + SRC]

Формат потока [LIVE]: поля без пробела после двоеточия (`event:result`), события разделены пустой строкой, после `started` идёт строка-комментарий `:`, поля `id:`/`retry:` отсутствуют.
Заголовки: `content-type: text/event-stream`, `cache-control: no-cache`, `expires: 0`, без `content-length`.

| Событие | data | Значение |
|---|---|---|
| `started` | `{"id":"<query_id>","online_probes":37,"target":"1.1.1.1"}` | Задание принято; `online_probes` — сколько сканеров ответят |
| `result` ×N | объект сканера (ниже) | Результат одного сканера; приходят по мере готовности |
| `done` | `{"id":"…","online_probes":37,"response_count":37,"status":"done"}` | **Единственный признак завершения** |

Результат сканера [LIVE]:

```json
{"asn":"AS12389","cdn_unblocked":true,"dns":null,"dpi_hop":2,"host_results":[],"job_id":"<query_id>",
 "probe_id":"50","provider":"Rostelecom","region":"Пермский край","target_hop":null,"verdicts":["tspu_block"]}
```
`verdicts` ∈ {`ok`, `tspu_block`, `sni_block`, `dns_spoofing`, `cdn_block`, `whitelist`, `uncertain`} [SRC]. Для проверки по IP `dns:null`, `host_results:[]`
(SNI и DNS проверяются только для доменов [DOC]). `target_hop`/`dpi_hop` — номера хопов TTL-трассировки; `target_hop:null` у блокирующих сканеров.

### Тайминг одного реального запуска (1.1.1.1, 37 сканеров)

| Момент от `started` | Что пришло |
|---|---|
| +0,09…1,3 с | 28 результатов (ok/uncertain) |
| +2,2 с | ещё 4 результата |
| **+8,1…8,4 с** | последние 5 результатов, **все `tspu_block`** |
| +8,4 с | `done`, `response_count = 37` |

Итого 37 из 37 за ~8,4 с. Блокирующие результаты пришли **последними** (по-видимому, это сканеры, ждавшие таймаута соединения).
Поэтому по первым секундам потока нельзя судить об итоге: до `done` картина «5 из 37 блокируют» была бы невидима. Это ключевая причина, по которой приложение ждёт `done`.

### Когда стартуют сканеры [ВЫВОД]
Между `/check` и открытием SSE прошло около 13 с, но результаты шли ещё ~8 с после `started`, а не отдавались разом. Значит задание запускается при подключении к `/probe/{id}`, а не при `/check`.
Следствие: один `/check` не запускает сканеры; запуск лимитируется именно подключением к SSE.

### Проверка домена [SRC + предоставленный образец]

Приложение передаёт нормализованный домен в `/check`, не разрешая его через DNS телефона. Ответ содержит `target_type: "Домен"`, `ips`, `rkn_domain` и CDN-данные; динамическая проверка запускается по выданному `id`. В предоставленном образце JWT содержит claim `ip`, равный первому адресу из `ips`, но одного этого недостаточно, чтобы утверждать, что все наблюдения динамики выполняются только по этому адресу.

Доменная запись `result` дополняет обычные поля сканера:

- `dns`: `spoofing_detected`, `suspicious_provider_count`, `verdict_threshold`, `samples_per_protocol` и наблюдения по resolver/protocol. Каждое наблюдение содержит provider, протокол, suspected-spoofing, коды ответа, счётчики IPv4/IPv6 и outcome (`Answer`, `NoRecords`, `Error`).
- `host_results`: записи с `host`, `host_id` и `probe_evidence.type`. Приложение сохраняет сырые типы и группирует их, не приписывая им неподтверждённый смысл.

Эти поля описаны типами фронтенда сервиса в [`probe.ts`](https://github.com/LowderPlay/cheburcheck/blob/master/frontend/src/lib/api/probe.ts). Для CDN применяется то же правило сайта: если `host_results` непуст, `cdn_unblocked` не true и среди вердиктов есть `ok`, он преобразуется в `cdn_block`; явные блокирующие вердикты имеют приоритет.

## 5. Итоговый вердикт (логика сайта) [SRC]

Порт `displayProbeVerdicts` / `selectProbeVerdict` реализован в `domain/Verdict.kt` и покрыт тестами на реальном потоке:
1. Вердикт `cdn_block` при адресе вне CDN-списков считается `ok`. Для адреса в CDN-списке `ok` превращается в `cdn_block`, если `cdn_unblocked≠true` и `host_results` не пуст (для IP он пуст, поэтому остаётся `ok`).
2. Если у сканера есть блокирующий вердикт (`tspu_block`, `sni_block`, `dns_spoofing`, `cdn_block`), `ok` отбрасывается.
3. Каждый сканер голосует за вердикт с высшим приоритетом: `tspu_block > sni_block > dns_spoofing > whitelist > cdn_block > ok > uncertain`.
4. Побеждает вердикт с наибольшим числом голосов; при равенстве выигрывает более приоритетный; победа `uncertain` означает «итога нет».

Для образца: 25 `ok`, 7 `uncertain`, 5 `tspu_block` → большинство `ok` (итог «доступен»). Приложение дополнительно показывает «блокировку увидели 5 из 37 сканеров», чтобы меньшинство не терялось.
То, что сайт считает «статическим CDN» (`isStaticCdn`), в приложении равно непустому `cdn_providers` [ВЫВОД: исходник не просматривался построчно].

## 6. Что приложение считает завершённой проверкой

| Состояние | Условие |
|---|---|
| Статика получена | HTTP 200 и JSON-объект от `/check` |
| Динамика ожидается | есть `id`, но слот запуска ещё не получен (лимитер) или SSE не открыт |
| Динамика идёт | SSE открыт, пришёл `started`/`result`, `done` ещё нет |
| **Завершена** | пришло событие `done` |
| Частично | поток оборвался/таймаут после ≥1 `result` без `done`; результаты сохраняются, итог не «завершён» |
| Ошибка | ни одного ответа после всех повторов |
| Недоступна | нет `id`, цель — CIDR, либо частный IP (настройка); для доменов динамика запускается по `id` ответа `/check` |

`blocked` из `/check` и отсутствие записей в списках **никогда** не дают состояния «Проверка завершена».

## 7. Лимиты, повторы, ошибки

| Факт | Источник |
|---|---|
| 5 запусков сканеров в минуту с одного IP; результаты кешируются ~3 ч | [2ND], вживую не проверялось |
| Ответ при превышении лимита: HTTP 429 или событие `error` в потоке (формат неизвестен) | [2ND] |
| За тестовую сессию (7 запросов `/check` с паузой 2–3 с и 1 SSE) ответов 429 не было | [LIVE] |

Реализация: общий скользящий лимитер (`StartLimiter`), по умолчанию 4 запуска/мин, настройка зажата в 1…5. HTTP 429 и in-stream `error` с `code:429` обрабатываются одинаково:
ожидание `max(Retry-After, 20 с × попытка)` и повтор. 5xx, таймауты, сетевые ошибки и битый JSON повторяются с экспоненциальной паузой (1,5 с, 3 с, 6 с…). 404 и 4xx не повторяются.
Таймаут ожидания сканеров по умолчанию 90 с (наблюдаемое время 8 с; это предохранитель от бесконечного ожидания, а не фиксированная пауза).

## 8. Неизвестное и ограничения

- Заголовки и тело 429 не наблюдались, лимит 5/мин и кеш 3 ч не проверены.
- Поведение SSE для частных адресов не проверялось; приложение по умолчанию не открывает для них SSE (переключается в настройках). Если после включения сервис ответит `done` с `response_count: 0`, итог будет «Результат неизвестен».
- Нужен ли параметр `token` в `/probe/{id}` у фронтенда [SRC]: запросы без него работают [LIVE]. Приложение его не использует и не пытается получить.
- Типы `blocked_subnets`, `whitelist`, `rkn_domain` не наблюдались.
- Подсеть целиком в `/check` приложение не отправляет: каждый адрес проверяется отдельно, как требует задача. Публичного массового API у сервиса нет.
- Адреса `.0` и `.255` подсети приложение проверяет как обычные IP (если не включено исключение); как ответит сервис на такие адреса, в образцах не проверялось.
